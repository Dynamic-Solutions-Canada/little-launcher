# Project architecture reference

Paths in this reference are relative to the LittleLauncher project unless stated otherwise.

`Models/WebLauncherPresets.cs` owns messaging service creation templates. The Add Launcher
menu creates independent, editable web launchers from them and opens their sign-in pages.

`Windows/WebFlyoutWindow.VideoFit.cs` owns optional fitting of contained fullscreen to a video's
intrinsic aspect ratio, including monitor bounds, pending-fit cancellation and temporary sizing.

`Windows/WebFlyoutWindow.FullscreenTitleBar.cs` owns the fullscreen header overlay,
top-edge hover detection, a contained-fullscreen maximize control that preserves page fullscreen,
and returning its existing controls to the normal chrome on exit.

`Windows/WebFlyoutWindow.ContentFullscreen.cs` owns the conditional fullscreen-video header
action, visible-target detection, and the user-initiated browser fullscreen request.

`Windows/AppPickerRowActions.cs` owns the unified app picker's full-target tooltips and
keyboard-accessible row context menus. Open shares `FlyoutWindow.Launch`; containing-folder
is available only for existing filesystem parents. Duplicate labels are computed against
the full catalog in `ItemEditorWindow` and exposed by `AppPickerEntry` without changing saved names.

`Windows/LauncherSettingsSections.cs` owns the ordered IDs and localized section labels shared
by launcher settings and the web flyout menu. `LauncherSettingsWindow.Sections.cs` assembles
sections with their initial expansion defaults and reveals explicit destinations; the
`WebGeneral`, `WebAppearance`, `WebSize`, `WebBehavior`, and `WebPrivacy` partials hold the
focused web control builders.
`WebFlyoutWindow.SettingsMenu.cs` provides quick controls and links into the same owned settings
window. Advanced retains menu-only troubleshooting.

`SettingsWindow.ItemEditing.cs` opens `Windows/LauncherItemsEditorWindow.cs`, a regular owned Mica window with normal title bar/app icon, shared toolbar, two-axis viewport and external Done. `Controls/LauncherItemsView` is the single item renderer/edit implementation shared with the native flyout through `ILauncherItemsHost`. Settings cards/navigation remain visible normally. The editor preserves intrinsic item geometry and scrolls rather than reflows; edits save immediately. Done/Escape/close ends it, while minimize/app switching retains it. Same-launcher tray/taskbar entry focuses it or its owned dialog; different launchers can edit independently. New-launcher setup opens the same regular editor at the captured setup bounds/monitor, owned by Main Settings. No persisted geometry or launcher identity changes are involved.

Web launcher cards use a single **Settings** row with the address or **No web address set** as its subtitle, opening the same launcher settings window and refreshing the cards on return.


## Architecture

- **Single-instance app** enforced via a named `Mutex` ("LittleLauncher"). A second launch signals the first instance via `PostMessage` with registered window messages (`LittleLauncher_ShowFlyout_{launcherId}`, `LittleLauncher_ShowSettings`).
- **Launchers**; users define one or more named `Launcher` objects (model: `LittleLauncher.Models.Launcher`). Each launcher has its own `Items` collection, tray icon (mode + optional custom path), and `NIconHide` visibility flag. Settings include a `Launchers: ObservableCollection<Launcher>`. On first run with old settings, the legacy `LauncherItems` list is migrated into a "Default" launcher.
- **Launcher kinds**; `Launcher.Kind` decides what the tray icon opens: `LauncherKinds.Items` (0, the default; a `FlyoutWindow` of launcher items) or `LauncherKinds.Web` (1; a `WebFlyoutWindow` showing `Launcher.WebUrl`). **Never call `FlyoutWindow.Toggle` directly**: `Windows/LauncherPanels.cs` is the single place that resolves a launcher's kind, and every tray click, pinned shortcut and settings entry point routes through it.
- **MainWindow** is invisible (moved off-screen, 1×1). It owns one native tray icon per launcher via `Shell_NotifyIcon` (stored in `_trayIcons: Dictionary<string, TrayIconEntry>`). Tray and notification clicks share `TryResolveTrayAnchorPoint` to anchor to that icon's rectangle from `Shell_NotifyIconGetRect`. When unavailable, notifications try the taskbar button before falling back to the cursor. Uses `WS_EX_TOOLWINDOW` to hide from Alt-Tab.
- **FlyoutWindow** is the native popup host for the shared `LauncherItemsView`. Supports two view modes per launcher: list view (icon + name side by side) and icon grid view (larger icon with name below, configurable icons-per-row wrapping grid). **A list column is as wide as the longest label the launcher holds**, capped at the 175px every column used to be and floored at 80, with one width shared by every column - ragged columns read as a broken table. `ComputeListColumnWidth()` decides it once per rebuild from measured label *strings*, never from laid-out content, and both the columns and the window sized around them read the cached answer. One instance is maintained per launcher (`_instances: Dictionary<string, FlyoutWindow>`), created up front by `WarmUp()` and parked off the virtual screen to compose its first frame; a window WinUI has never drawn presents a black rectangle when it is first shown. **Dismissing parks the window off the virtual screen rather than hiding it** (`ParkOffScreen`); `ShowWindow(SW_HIDE)` let WinUI release the composition surfaces, so the next cold open spent ~100ms re-rasterising every text run and item icon and the flyout slid in as an empty rectangle with the items popping in at the end. Because the window is therefore visible in the Win32 sense for the life of the app, **`_isOpen`; not `WS_VISIBLE`; is the test for "the flyout is open"**. Shown from a launcher's tray icon click, positioned above the taskbar, and when `UserSettings.FlyoutAnimationsEnabled` is on the full rendered window slides in and out from its anchored edge using short eased position updates, dismissed on focus loss or Escape. In icon mode, top-level groups are arranged by the custom `PackedIconPanel`, which lets narrower groups share a row beside wider groups while keeping row height based on the measured group content, and dragging near the flyout's left or right edge snaps the layout wider or narrower by whole icon columns and persists `Launcher.IconModeIconsPerRow` immediately.
- **Launcher item editing** uses `Controls/LauncherItemsView` in two window hosts. The native tray flyout retains its hover pencil, floating toolbar, blue DWM edit border and dismissal suppression. Settings-origin editing uses a normal owned `LauncherItemsEditorWindow` with the same templates, commands and custom drag/drop, an inline toolbar, a two-axis viewport and an external Done button. Both save immediately. The shared view preserves item/column geometry and computes intrinsic size; only the native host clamps height to its monitor. External drops use `LauncherItemsView.ExternalDrop.cs` and `DroppedItemFactory`; owned item/group/launcher-settings dialogs retain their existing implementations. See [drag-drop.md](drag-drop.md).
- **WebFlyoutWindow** (`Windows/WebFlyoutWindow.cs`) is the flyout a web launcher opens: a borderless, always-on-top, tray-anchored window hosting a **WebView2** on the launcher's URL, with a slim header (back, forward, reload, a **"…" menu** of per-moment options, **zoom** among them, an **Advanced** submenu (developer tools, reload ignoring cache, turn on notifications, rebuild this launcher's notification bridge or every launcher's) and launcher settings at its foot, open in browser, pin, minimize in regular-window mode only, maximize, close), a **tab strip** and an optional address bar beneath it (`Launcher.WebShowAddressBar`, off by default; the "…" menu carries the setting). **Every browser it owns is a tab** (`Windows/WebFlyoutWindow.Tabs.cs`): a link asking for a new window becomes one rather than leaving for the real browser, and the strip appears on its own once there are two (or always, under `Launcher.WebAlwaysShowTabs`). Tabs the *launcher* owns; its address, or each bookmark under `WebBookmarksAsTabs`; are the only ones allowed to write its icon or be re-navigated by a settings change; a tab opened from a link is the user's own place and nothing configured may move it. It presents like `FlyoutWindow` but its resource model is the **opposite**: nothing is created until the user first opens it (it is deliberately excluded from `WarmUp`), and dismissing it collapses the control, calls `CoreWebView2.TrySuspendAsync()` and drops `MemoryUsageTargetLevel` to `Low`; except under `WebHiddenPolicies.KeepRunning`, which only collapses, because both the memory hint and Chromium's background throttling stop a hidden page receiving at all (the throttling is disabled for the whole environment in `Services/WebViewEnvironments.cs`). Under the default `WebHiddenPolicies.UnloadWhenIdle` the whole browser is then closed after `Launcher.WebIdleUnloadMinutes`, so a hidden dashboard costs nothing at all. Each web launcher gets its own WebView2 user-data folder (`%AppData%\LittleLauncher\WebProfiles\{launcherId}`), so logins survive restarts and launchers stay signed in independently. **Camera, microphone, location and notification requests are answered in the flyout's own prompt bar** and remembered per profile (`Windows/WebFlyoutWindow.Permissions.cs`); there is deliberately no "trust this site" shortcut, because a site handed a grant it never asked for skips the flow that grant implies, and for notifications that flow is what registers the push worker; **Turn on notifications** makes a site that will not ask call `requestPermission()` rather than writing the permission behind its back; page notifications become Windows toasts; each carrying a **header with its launcher's name**, so Notification Center files them under the launcher rather than under the app, and each **withdrawn again** when the page closes the notification, when the launcher is brought to the front, when its header is clicked, when the launcher is deleted, or on the next reboot. A launcher also holds at most five at once, because the Action Center queue is per *app* and every launcher shares one, so a launcher that withdraws nothing evicts the rest; and since a suspended or unloaded browser raises none, granting notifications *offers* to switch that launcher to `WebHiddenPolicies.KeepRunning` rather than doing it silently. **WebView2 surfaces only non-persistent notifications**, so the page's `showNotification` is rewritten to that flavour, and the service worker; which a document script cannot reach; is bridged by serving the shim followed by the site's own script **inlined** as it is fetched (`WebFlyoutWindow.IconPreview.cs` (non-mutating loaded-page icon preview); `WebFlyoutWindow.ServiceWorker.cs`), which is also what makes toast **action buttons and inline reply** run the app's own `notificationclick` handler. **The wrap can never `importScripts` the URL it is served at**; that resolves out of the registration's script resource map, which already holds the wrap, so it imports itself until the stack gives out; and a site that serves its worker only to a request carrying `Service-Worker: script` (Messenger) needs that header put on through the DevTools protocol, since a page is forbidden from setting it. The window is fully borderless (no non-client area), so it has no system sizing border: resizing is done with invisible XAML edge/corner grips that drive `SetWindowPos` and persist the dragged size onto the launcher. **Maximize is temporary**; the header's maximize fills the monitor's work area and is dropped on dismissal, so it is never written to the launcher. **Double-clicking the caption does the same thing in both directions**, the caption being the three strips that already drag the window (header, empty tab strip, empty bookmark bar); it is counted inside `BeginWindowMove` against the system's own double-click time and slop, because those strips take their own `PointerPressed` and XAML then raises no tap gestures. **Resting on that button** instead drops a picker of places to send the window, drawn as a 3x3 grid of little screens the way Windows 11 hangs snap layouts off the same button. It **moves the window and writes nothing** - it borrows nine of the presets the "Opens at" setting uses and shares only their labels with it. The other two anchors are rules about opening rather than places, so they stay in the menu. **Always-on-top is a band, not a place**: several launchers can be in it at once, so the one that takes focus re-asserts its place at its head (`RaiseWithinTopmostBand`) and `SetTopmost` refuses to re-apply a value the window already has, or a background favicon fetch on one launcher pushes it in front of the one being read. **A web launcher is a home page plus a bar of bookmarks.** `Launcher.WebHomeUrl` is where it opens and is a setting of its own, not a position in the bar (an earlier design made it the first bookmark; folders ended that, since position zero can hold something with no address). Empty falls back to the first bookmark, so files written before it behave unchanged, and a bookmark holding the same URL is an ordinary bookmark nothing tries to merge. Read it through `Launcher.WebAddress`. The bar appears as soon as there is a second bookmark (`Launcher.ShowsBookmarkBar`), with no setting behind it. **The bar takes folders** (`WebBookmark.IsFolder` + `Children`, the same shape a group takes in an item launcher): one draws with a folder glyph, opens a menu of what it holds, nests without a depth limit, accepts a bookmark dropped onto it or filed through **Move to folder**, and gives its contents back to the bar when removed. **The bar otherwise holds no state** (`Windows/WebFlyoutWindow.Bookmarks.cs`): it opens pages the way a browser's does; a click loads the bookmark in the tab in front, a middle-click or Shift/Ctrl-click opens a new tab, clicking the bookmark for the page already showing simply loads it again, and nothing in the bar is tinted. There is no collapsed state and no per-bookmark browsers; extra tabs are made only by the gestures that ask for one. **It is also edited from the bar**: a star at the end of the address bar adds or removes whatever the address box shows (the "…" menu carries the same action, since the address bar is off by default), right-clicking a bookmark opens it (here or in a new tab), renames, re-addresses, copies, defaults, moves or removes it, and dragging one reorders the bar, and the bar's own menu carries **Icons only**, the launcher-wide switch that drops every label. Launcher settings still holds the full list. See [.codex/docs/web-launchers.md](web-launchers.md).
- **SettingsWindow** uses Mica and NavigationView page navigation. Launchers cards open `LauncherSettingsWindow` for launcher settings and `LauncherItemsEditorWindow` for Items; the sibling ellipsis retains bulk operations. New shortcut setup continues into that same regular item editor, initially centred at the captured setup-window bounds on that monitor. The shared `LauncherItemsView` retains the exact native item layout inside a scrolling viewport, and Done closes the editor with changes already saved. Web launchers skip item editing.
- **Settings** are serialised to `%AppData%\LittleLauncher\settings.json` via `System.Text.Json`, managed by the fully static `SettingsManager`. On first load, migrates from legacy `settings.xml` (XmlSerializer) to JSON.
- **Global sync** moves all launchers (as `launchers.json`) between machines, and is **transport-pluggable**: `UserSettings.SyncProvider` (see `Models/SyncProviders.cs`) selects SFTP (0, the default), OneDrive, Google Drive, a network file share, any other folder, or any WebDAV server. `LauncherSyncService` is the only entry point; it resolves the provider and dispatches to `SftpSyncService` (SSH.NET), `CloudSyncService` (a signed-in cloud account), or `FolderSyncService` (a directory, in `UserSettings.SyncFolderPath`). **OneDrive and Google Drive use their vendor APIs; Microsoft Graph and Drive v3; not synced folders**, so the upload is confirmed by the service, no sync client need be installed, and the remote's modified time can be read; each signs in through the system browser via `OAuthPkceClient` and stores tokens DPAPI-encrypted in `CloudTokenStore`, never in settings.json. **WebDAV** (Nextcloud, ownCloud, a NAS) rides the same `ICloudFileStore` path but with Basic-auth credentials typed into the app rather than a browser flow; no registration, consent screen or vendor review, because it is a standard rather than a product. Adding another account provider means implementing `ICloudFileStore` and nothing else. Folder providers serve everything else; Dropbox, Seafile, Syncthing, and OneDrive for Business, which cannot use the app-folder permission. **Never call a transport directly from outside `Services/`**; and never gate a trigger on `SftpHost`, which is meaningless under any other provider. The wire format, the newer-local download guard, the merge and the atomic write live in `LauncherPayload` so the transports cannot drift apart. See [.codex/docs/sync.md](sync.md).
- **SftpSyncService** also handles per-launcher shared sync, which is a separate feature with its own per-launcher transport (`Launcher.SharedSyncMode`: file path or SFTP) and is unaffected by `SyncProvider`. Its transport is `Launcher.SharedSyncMode` (`Models/SharedSyncModes.cs`): File (0), SFTP (1) or WebDAV (2); **WebDAV is the cleanest for person-to-person sharing**, since the URL is already a shared address and both sides can write. The cloud-account providers are deliberately absent: OneDrive's app folder and Google's app-data folder are private per-user storage that cannot be granted to anyone else. It supports 1-way (owner pushes, subscribers pull) and 2-way (all participants push and pull, last save wins) modes. `AutoSyncService` skips automatic downloads while local launcher item edits are still pending upload so periodic syncs do not overwrite newer local flyout/editor changes. A merge leaves a launcher's `Items` untouched unless the download differs (`LauncherPayload.ItemsMatch`) and rebuilds the flyout of any launcher whose items it did replace, because **a flyout's rows hold the item objects themselves** and equal-valued copies leave remove, move and edit looking up items the launcher no longer contains. Periodic/shared downloads then refresh flyouts via `FlyoutWindow.InvalidateItems(force: false)` and `WebFlyoutWindow.InvalidateBookmarks()` (a merge hands the launcher new `WebBookmark` objects, so a bar built before the sync is left holding bookmarks the launcher no longer contains); a no-op sync then skips the rebuild instead of tearing down and re-creating every flyout's visual tree on a timer (that unnecessary rebuild churn drove a large container-leak; see [.codex/docs/drag-drop.md](drag-drop.md)).
- **Taskbar jump lists** (`Services/JumpListService.cs`) put a launcher's own contents on the menu Windows shows when its **pinned taskbar button is right-clicked**: its items, flattened exactly as the flyout flattens them, or its bookmarks for a web launcher. **The list belongs to an AppUserModelID rather than to a process**, which is what allows one per launcher: `Launcher.PinAumid` already records one per pinned launcher, and for launchers pinned before the app recorded it, the taskbar's own pin store is read as a fallback (for publishing only, never as window identity). **Nothing published can be a live menu** - the shell never says a jump list was opened - so it is republished on `SettingsManager.Saved`, debounced, and skipped when the resulting list is unchanged. A **web launcher with a single address publishes nothing**, since its one entry would go exactly where clicking the button already goes. Every task runs the companion exe with a position and a **token identifying the entry by content**, so a list left over from before an edit either finds its entry or falls back to opening the launcher, and a **bookmark opens in a new foreground tab** rather than taking over whatever the launcher was left on. **Below a separator sit the launcher's own commands** (`Models/LauncherActions.cs`): launcher settings, edit items or open in browser depending on kind, and the app's settings. They are never what gets trimmed when Windows is short of room, and a launcher with nothing to list still gets them. **The heading is Windows' word "Tasks" and cannot be changed** - see [.codex/docs/pinvoke.md](pinvoke.md).
- **LauncherShortcut** (`LittleLauncherFlyout.exe`) signals the host via launcher-specific `PostMessage` messages. Normal launch, jump-list tasks (`--item`/`--token`) and launcher actions (`--action`) stay lightweight. Explicit `--pin` uses `TaskbarPinning` (foreground STA timer and raw WinRT COM), `PinShortcut` (one physical Start snapshot per launcher with cancellation rollback), `PinWindow` (+ `PinWindow.Appearance.cs`, rounded foreground reminder card with transparent icon drawing and an unshown query pump), and `ShellInterop`/`NativeMethods`. Actual process package identity, desktop API support and LAF requirements gate Windows confirmation; unsupported systems retain manual pinning. The old saved identity is queried live in a separate bounded read-only process before snapshot replacement; the pinning process retains one new startup identity before any UI or WinRT. Known unpinned skips warnings, known pinned with unchanged confirmed details returns already pinned, and unresolved old identity permits a fresh attempt without a removal warning while diagnostics remain Unknown. `--check-only` reuses that read-only phase without pin submission. New AUMIDs use `LittleLauncher.Launcher.{id}.{guidStamp}`; only confirmed native/manual pins replace local `Launcher.PinAumid`. Shortcut-backed identities never carry simultaneous window relaunch metadata. Release remains Native AOT. See [icons.md](icons.md).

Launcher settings reads live pin state through `TaskbarPinStatusService` and the companion's
isolated unshown `--check-only` phase. Open/activation refreshes the per-identity cache; typed names,
saves and rendered-icon events only recompute details. The ordinary row subtitle hides replacement
warnings for known absence or unresolved old state, and reports Pinned for a known unchanged pin.
Unknown remains distinct in diagnostics; history/pending markers alone do not force manual recovery. Queries are serialized/cancelled on close and reaped before pin replacement.
